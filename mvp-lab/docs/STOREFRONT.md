# 스토어 화면과 주문 저장 경계

[GoogleCloudPlatform/microservices-demo의 Online Boutique](https://github.com/GoogleCloudPlatform/microservices-demo)는 상품을 탐색하고 장바구니에 담아 주문하는 데모입니다.
그 흐름을 참고해 기존 MVP의 첫 화면을 쇼핑몰 형태로 구성했습니다. 상품 상세, 장바구니, 주문 확인, 영수증을 제공하고,
주문 내역·저장소 대조·연결 상태·실습 가이드로 이어집니다.

## 이용 순서

1. **상품 탐색:** 카테고리와 이름 검색으로 상품을 고르고 가격순으로 정렬합니다. 상품 이미지는 페이지에 포함된 SVG입니다.
2. **상품 상세:** 상세 창에서 상품 설명·가격·수량을 확인하고 장바구니에 담습니다.
3. **장바구니:** 여러 상품을 함께 담고 수량을 바꾸거나 상품을 삭제합니다. 상품별 금액과 전체 합계를 확인합니다. 빈 값·0·소수·범위를 벗어난 수량은 즉시 안내하고 주문을 막습니다. 삭제 뒤 키보드 포커스는 가까운 상품으로 이어집니다.
4. **주문 확인:** 장바구니 내용을 다시 확인한 뒤 데모 주문을 확정합니다. 실제 결제는 발생하지 않습니다.
5. **주문 영수증:** 저장된 주문 합계와 상품별 상태·버전·주문 ID를 확인하고 상세로 이동합니다. 원본 조회·상태 변경으로 확인한 새 버전은 영수증에도 보관합니다. 오래된 캐시 조회로 영수증 버전을 낮추지 않습니다. 주문 내역에서도 각 주문을 조회할 수 있습니다.
6. **저장소 관찰:** 주문 상세의 읽기 전용 대조로 MariaDB 원본과 Redis 캐시·Elasticsearch 검색 문서의 상태·버전을 비교합니다.

검색 결과가 없으면 **전체 상품 보기**로 검색·카테고리·정렬을 초기화합니다. **쇼핑 계속하기**는 상품 컬렉션 위치로 이동하며, **본문으로 건너뛰기**는 현재 화면을 유지하고 본문으로 이동합니다.

기존 고정 상품은 데일리 무선 키보드, 포레스트 테이블 램프, 모닝 세라믹 머그, 에어 오버이어 헤드폰입니다.
표시된 상품·가격은 실습용 예시입니다. 재고 확인, 회원 계정, 고객 정보, 배송 주소, 카드 입력, 실제 결제·배송 처리는 제공하지 않습니다.
직접 상품명·수량·단가를 입력하는 기존 주문 등록도 주문 내역에서 계속 사용할 수 있습니다.
직접 입력 주문은 요청을 보내기 전에 **상품명·수량·단가와 요청 키를 현재 탭의 `sessionStorage`에 함께 보관**합니다.
응답을 받지 못했거나 새로고침했다면 같은 탭에서 직접 입력 창을 다시 열고 같은 요청으로 재시도하세요.
입력값은 저장 결과를 확인할 때까지 잠기며, 요청 내용과 일치하는 정상 주문 응답을 확인한 뒤 재시도 정보를 지웁니다.
브라우저 보관을 사용할 수 없으면 화면에 안내합니다. 이 경우 현재 화면에서 재시도할 수 있지만 새로고침 뒤에는 요청 정보를 복원할 수 없습니다.
탭을 닫거나 저장 데이터를 지워 요청 키를 잃었다면 새 주문을 입력하기 전에 주문 내역에서 저장 결과를 확인하세요.

뒤로가기나 hash 경로 이동은 열린 창을 닫고 이동한 화면을 사용할 수 있게 합니다.
직접 입력 창을 닫거나 다른 화면으로 이동한 뒤 도착한 저장 응답은 주문 상세를 다시 열지 않습니다.
재시도 정보는 남겨 두므로 직접 입력 창을 다시 열고 같은 요청으로 저장된 주문을 확인하세요.

## 장바구니 보관

장바구니는 서버 DB나 Redis가 아닌 **현재 브라우저 탭의 `sessionStorage`**에 저장합니다.
같은 탭의 새로고침에서 복원되며, 탭을 닫거나 브라우저 저장 데이터를 지우면 이어서 이용할 수 없습니다.
계정·다른 기기 사이의 장바구니 동기화는 없습니다. 브라우저 저장 기능을 사용할 수 없는 환경에서는 새로고침 후 보관을 기대하지 마세요.

화면은 `frontend/src`의 React 컴포넌트로 구성합니다. 상품 탐색·장바구니·주문 내역·주문 상세·연결 상태·실습 가이드를 나누고,
장바구니 상태와 재시도는 `useCart` 훅에서 관리합니다. 상품 SVG도 React 컴포넌트입니다.
React·React DOM과 Vite·React 플러그인의 버전을 고정하고 `package-lock.json`을 보관합니다. API와 6개 컨테이너 구성은 기존 경로를 사용합니다.

## React 개발과 빌드

일반 이용은 `./all.sh mvp up`으로 충분합니다. 컨테이너 빌드의 Node 22 단계에서 화면을 빌드하므로 호스트 Node.js는 필요하지 않습니다.
개발과 모의 브라우저 검사에는 Node.js 22.12 이상을 권장합니다. 프로젝트 루트에서 실행합니다.

```bash
npm --prefix mvp-lab/frontend ci
npm --prefix mvp-lab/frontend test
npm --prefix mvp-lab/frontend run build
```

빌드 결과는 `mvp_app/static/index.html`과 `mvp_app/static/assets/`에 생성하며 Git에 넣지 않습니다.
API가 이 파일을 같은 origin에서 제공하고 CSP로 외부 스크립트와 인라인 스크립트를 차단합니다. 런타임 CDN은 사용하지 않습니다.
실제 화면 소스·의존성 lock과 빌드된 자산은 런타임 계약에서 각각 해시로 확인합니다.

개발 서버는 다음 명령으로 시작합니다. 터미널에 출력된 로컬 주소를 열면 됩니다.

```bash
npm --prefix mvp-lab/frontend run dev
```

Vite는 `/api`와 `/health`를 기본 `http://127.0.0.1:18090` API로 전달합니다. DB 연동을 확인하려면 MVP를 먼저 기동하세요.
별도 API 포트를 사용할 때는 `MVP_API_URL=http://127.0.0.1:18311 npm --prefix mvp-lab/frontend run dev`처럼 지정합니다.
프록시는 브라우저의 Host와 Origin을 유지하므로 개발 화면에서도 주문 저장·상태 변경을 사용할 수 있습니다. API의 외부 Origin 거부는 유지합니다.
페이지 간 이동은 hash 경로를 사용하며 별도 라우터·서버 장바구니·상품 서비스는 추가하지 않았습니다.

## 여러 상품 주문과 부분 실패

기존 주문 API는 **상품명·수량·단가를 가진 주문 하나**를 저장합니다.
장바구니를 확정하면 화면이 각 상품을 순차 요청하고, 상품마다 별도의 주문 ID와 요청 키를 사용합니다.
장바구니 전체를 묶는 새 주문 API나 전체 상품에 대한 하나의 DB 트랜잭션은 없습니다.

예를 들어 키보드 저장이 성공한 뒤 머그 저장이 실패하면 키보드는 이미 주문으로 남습니다.
영수증에는 저장된 키보드 주문을 표시하고, 머그는 장바구니에 남겨 재시도할 수 있게 합니다.
화면이 저장 성공을 확인한 상품만 장바구니에서 제거합니다. 일부 저장을 전체 주문 성공으로 표시하거나 이미 저장한 상품을 자동 취소하지 않습니다.

타임아웃이나 연결 끊김은 서버에서 쓰기가 완료되지 않았다는 뜻이 아닙니다.
저장되지 않은 것으로 보이는 상품도 **같은 내용과 같은 요청 키로 재시도**해야 기존 주문으로 복구할 수 있습니다.
요청 키는 장바구니와 함께 보관합니다. 실패 뒤 장바구니나 브라우저 저장 데이터를 지워 새 주문을 만들면 동일한 구매 의도를 자동으로 식별할 수 없습니다.
요청한 상품은 저장 결과를 확인할 때까지 수량 변경·삭제를 잠급니다. 같은 요청으로 재시도해 결과를 먼저 확인하세요.
이미 저장된 상품은 영수증·주문 내역에서 먼저 확인하세요.

영수증의 저장 성공은 MariaDB 주문 저장 결과입니다. Kafka 전달이나 Elasticsearch 반영 완료를 의미하지 않습니다.
상품별 상세에서 읽기 전용 대조와 검색 반영 자동 확인을 사용해 실제 처리 상태를 관찰하세요.

Redis에 잘못된 주문 형식이나 `NaN` 같은 비표준 숫자가 있으면 일반 상세 조회는 MariaDB 원본으로 복구합니다.
읽기 전용 대조는 캐시를 고치거나 지우지 않습니다. JSON을 읽을 수 없는 캐시는 **조회 실패·비교 불가**로 표시합니다. 대조와 복구의 결과를 구분해 확인하세요.

Elasticsearch 검색은 결과 구조·주문 필드·문서 ID와 주문 ID의 일치·전체 건수 정보를 검증합니다.
손상되거나 불완전한 결과는 일부 행을 조용히 누락하지 않고 HTTP 503으로 안내합니다. 이 검사는 검색 문서를 고치거나 지우지 않습니다.

## 브라우저 검사 범위

위 절차로 React를 빌드하고 [품질 가이드](../../docs/QUALITY-GUIDE.md)의 Playwright·Chromium을 준비한 뒤 프로젝트 루트에서 실행합니다.

```bash
python scripts/test-ui.py
```

기존 [UI smoke](../tests/ui_smoke.js)와 Chromium 실행기가 실제 빌드된 HTML·JS·CSS를 로드해 **1280px·390px·320px** 화면에서 상품 탐색·장바구니·주문·영수증,
부분 실패 후 재시도, 기존 주문 조회·저장소 대조, 키보드 조작과 화면 넘침을 검사합니다.
필요한 브라우저 의존성은 [품질 가이드](../../docs/QUALITY-GUIDE.md)를 따릅니다.
검사 결과의 통과 여부는 실제 명령 출력으로 확인하세요. 이 문서는 검사 범위를 설명하며 과거 검사 결과를 이번 변경의 통과 증거로 재사용하지 않습니다.

스토어 검사의 **HTTP 응답은 모의 데이터**입니다. 추가 개발 프록시 검사는 별도 Vite와 실제 Python HTTP 핸들러를 실행해
브라우저가 생성한 Origin으로 주문 저장·상태 변경이 성공하고 외부 Origin은 거부되는지 확인합니다. 이 API의 DB는 테스트 대역입니다.
기존 실행 환경이나 실제 MariaDB·Kafka·Elasticsearch·Redis에 접속하지 않으며, 컨테이너 기동·데이터 지속성·장애 복구·HA를 증명하지 않습니다.
실제 DB 경로는 별도의 [런타임 인수 가이드](RUNTIME-ACCEPTANCE.md)에 따라 확인합니다.
기존 [화면·기동 고도화 기록](UI-UPGRADE.md)과 [검증 기록](VALIDATION.md)은 해당 날짜의 증거이며 이번 스토어 변경의 실기동 결과가 아닙니다.
