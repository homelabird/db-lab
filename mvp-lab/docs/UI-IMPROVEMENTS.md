# MVP 디자인·기능 개선 분석

이 문서는 첫 개선 단계의 기록입니다. 후속 전체 주문 검색·페이지·자동 확인과 실제 Docker 연동 증거는 [화면·기동 고도화](UI-UPGRADE.md)를 확인하세요.

2026-10-03, 현재 저장소의 화면·API·테스트와 Chromium 렌더링을 기준으로 분석했습니다.
상품 선택 → 주문 저장 → 상세 조회 → 상태 변경 → 저장소 대조 → 장애 관찰을 직접 확인했습니다. DB는 테스트 대역을 사용했습니다.
평가 기준은 첫 진입 접근성, 단계별 피드백, 같은 주문으로 비교할 수 있는 재현성, 운영 판단에 도움이 되는 정보입니다.

## 아쉬운 점과 적용한 개선

| 우선순위 | 기존 아쉬운 점과 영향 | 적용한 개선 | 확인 방법 |
|---|---|---|---|
| 높음 | 저장소 대조가 Redis·검색의 짧은 판정만 보여줘 원본 상태·버전과 차이를 파악하기 어려움 | 세 저장소를 각각 표시하고 상태·버전·다른 항목을 함께 제공. 원본 변경·검증 실패는 비교 불가로 안내 | 버전 불일치·검색 미반영·원본 장애·관찰 중 변경 브라우저 검사 |
| 높음 | 목록은 최초 로드 후 재진입해도 갱신되지 않으며, 연결 상태는 별도 클릭 전까지 비어 있음 | 해당 화면 진입 시 목록·진단 조회. 스토어·가이드 진입에는 숨겨진 목록 요청을 보내지 않음 | 외부에서 생성한 주문의 재진입 표시, 진단 자동 호출 검사 |
| 높음 | DB 연결 결과를 업무 완료로 오해하기 쉬우며 장애별 기능 영향을 알기 어려움 | 장애 서비스의 기능 영향을 설명하고, 연결이 성공해도 outbox·consumer lag가 남으면 처리 대기 안내 | Redis 장애의 SQL 우회 설명, 연결 성공+처리 대기, 진단 실패 후 이전 결과 제거 검사 |
| 높음 | 응답이 오지 않으면 버튼이 계속 비활성화되고 쓰기 완료 여부를 판단하기 어려움 | 모든 웹 요청에 20초 대기 제한. 결과 불확실성·원본 확인 안내. 생성 재시도의 기존 키를 유지하고 이미 저장된 주문임을 표시 | 저장 후 응답 유실·시간 초과·중복 제출·같은 키 재시도 검사 |
| 중간 | 최근 100개 밖의 주문을 UI에서 직접 열 수 없음 | 기존 상세 API로 전체 주문 ID 조회. 최근 목록 한도와 이전 주문 조회 방법을 표시 | 목록 밖 ID 조회·존재하지 않는 ID의 오류 복구 검사 |
| 중간 | 작은 모바일 버튼과 연한 보조 글씨, 숨겨진 버전으로 조작·비교가 어려움 | 버튼·입력 높이 44px, 주요 보조 글씨 색·상품 설명 크기 개선, 모바일 버전 표시 유지. 목록 ID는 요약하고 상세에 전체 ID 제공 | 1280×900·390×844·320×740 검사와 한글 화면 확인 |
| 중간 | 상품 주문 취소 후 직접 입력을 열면 상품명·가격·수량이 남아 의도치 않은 입력 가능 | 카탈로그에서 직접 입력으로 바뀔 때 기본값 복원. 실제 주문 시각·원화 단위와 결제·배송의 실습 상태 안내 | 입력 모드 전환·합계·수량 검증·키보드 모달 검사 |
| 중간 | 첫 화면에서 학습 목적과 첫 장애 실습 순서가 잘 드러나지 않음 | 스토어에 실습 시작 안내, 가이드에 정상 기준 → Kafka 중단 → 새 주문 관찰 → 복구 확인의 네 단계 제공 | 스토어·가이드 렌더링, 안내 링크 및 실제 API 주문·대조 흐름 확인 |

기존 상품 일러스트·스토어 구성과 단일 HTML 구조를 활용했습니다. 서버 API, DB 스키마, 의존성은 추가하지 않았습니다.

## 적용과 다음 검증

실행 중인 API 이미지에는 화면이 포함되므로 새 화면 적용에는 API 이미지 재빌드가 필요합니다.
기존 설정·볼륨을 유지하며 `./all.sh mvp up`으로 재빌드·기동하고, `./all.sh mvp smoke` 후 웹 가이드의 첫 실습을 진행하세요.
이번 작업에서 기존 스택 기동·중단이나 사용자 DB 변경은 수행하지 않았습니다.

남은 제약은 실습 목적과 별도로 판단해야 합니다.

- 상품은 고정 예시이며 재고·결제·배송 시스템은 없습니다. 실제 판매가 목적이면 상품 API와 서버 가격 검증부터 필요합니다.
- 원본 목록은 최근 100개, 검색은 최대 50개입니다. 오래된 주문을 ID로 조회할 수 있지만 전체 목록 탐색에는 서버 페이지 조회가 필요합니다.
- 대조는 순차 관찰입니다. SQL의 관찰 전후 값이 같아도 네 DB 전체의 원자적 일관성이나 과거 장애 원인을 증명하지 않습니다.
- 진단은 연결과 대기량입니다. worker 처리 완료·실제 전달 경로는 주문 ID·버전 대조와 `smoke`로 확인해야 합니다.
- 단일 노드·한 worker의 학습 구성입니다. 여러 worker, 운영 인증·TLS, HA나 성능 평가에는 별도 설계와 실제 런타임 인수가 필요합니다.

실제 DB 인수 절차는 [런타임 인수 가이드](RUNTIME-ACCEPTANCE.md)를 따릅니다.
