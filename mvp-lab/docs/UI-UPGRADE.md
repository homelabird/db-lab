# MVP 화면·기동 고도화 — 2026-10-03

첫 화면과 접근성 개선은 [이전 분석](UI-IMPROVEMENTS.md)을 따릅니다. 이번 변경은 주문이 많거나 검색 반영이 늦을 때의 확인 흐름과, 설정 오류를 발견하기 전에 다른 스택을 시작·종료하던 공통 기동 순서를 개선합니다.

## 화면에서 확인하기

1. 주문 내역의 원본 탭에서 상품 이름·주문 ID를 검색합니다. 검색은 전체 MariaDB 주문을 대상으로 하며 25개씩 이전·다음 페이지로 읽습니다. 상태 선택은 첫 페이지로 돌아갑니다. 조건을 수정하고 새로고침해도 이전 cursor를 재사용하지 않습니다.
2. 상세의 주문 ID 복사로 동일 주문을 계속 추적합니다. 브라우저가 복사를 허용하지 않으면 표시된 ID를 직접 복사할 수 있습니다.
3. Kafka 중단 후 새 주문을 만들고 상세의 검색 반영 자동 확인을 켭니다. 5초마다 읽기 전용 대조를 실행합니다. 원본이 관찰 중 안정적이고 검증 가능하며 ES와 일치하면 자동 확인을 종료합니다.
4. 연결 상태에서 자동 갱신을 켜면 의존 서비스·대기량을 5초마다 읽습니다. 연결 성공은 전달 완료를 뜻하지 않습니다. 상세를 닫거나 해당 화면을 숨기거나 탭이 백그라운드로 가면 자동 요청을 멈춥니다. 진행 중 요청과 겹치지 않습니다.

별도 UI 프레임워크·상품 DB·추가 서비스는 넣지 않았습니다. 검색 목록은 원자적 스냅샷이 아니며, 페이지 사이에 상태가 변경될 수 있습니다. 검색·상태 필터는 작은 실습 데이터에서 스캔할 수 있으므로 대용량 성능 근거로 사용하지 않습니다. API 파라미터는 [README](../README.md)에 설명합니다.

## 기동 순서와 실패 해석

공통 `all.sh up/restart`:

```text
전체 preflight → 선택 전체 초기화 → 선택 전체 doctor
→ 첫 프로젝트 시작 + health → 다음 프로젝트 시작 + health → …
```

초기화·doctor 실패는 시작·종료 전에 배치를 중단합니다. `restart`는 이 검사 후 각 프로젝트의 `down → up`을 실행하고 종료 실패 뒤 다시 시작하지 않습니다. 기본 대상은 기존 네 HA 실습과 MVP를 유지합니다. 다른 공통 명령의 기본 대상은 기존 네 실습입니다.

시작 명령이 성공해도 최대 60초 health 확인이 실패하면 실패입니다. `READY`와 receipt의 `health_verified=true`는 읽기 전용 애플리케이션/토폴로지 검사 통과를 뜻합니다. 실제 쓰기·지속성·복제·장애 전환 증거는 별도입니다. 부분 시작 후 자동 rollback이나 볼륨 삭제는 하지 않습니다.

MVP 내부:

```text
API/worker 빌드 → DB 4개 준비 → API 시작·schema/topic/index 초기화
→ worker 시작 → 전체 서비스 준비
```

핀된 로컬 Docker에서 각 준비 단계는 180초 한도와 서비스별 증거를 `reports/startup/`에 남깁니다. 실패하면 뒤 단계는 시작하지 않고 기존 컨테이너·볼륨을 보존합니다. `redis-spare` 모드의 보조 Redis도 검사합니다. 다른 provider의 컨테이너 준비는 `not_certified`로 남기며 API 초기화는 계속 확인합니다. `doctor`는 새 대상 identity를 고정하지 않고 기존 identity·엔진 pin·미완료 실습·잘못된 암호 실험을 검사합니다.

## 검증 범위

- 호스트 MVP 전체 879개, 루트 전체 268개, 최종 HTTP/기동 53개 검사와 정적 검사가 통과했습니다. SQL 필터 바인딩·literal wildcard, 같은 시각의 cursor 페이지, 페이지 사이 신규 삽입, HTTP 잘못된 파라미터, DB/API 준비 실패 시 뒤 단계 차단을 포함합니다.
- Chromium 모의 API 회귀는 1280×900·390×844·320×740에서 검색·상태 필터·페이지·복사·자동 확인·요청 중복 방지·키보드·레이아웃을 검사합니다. 이는 실제 DB 증거가 아닙니다.
- 별도 프로젝트 `db-lab-mvp-uiup-20261003`, loopback `28190`에서 Docker 29.7.2 / Compose v2.40.3의 실제 6개 컨테이너를 기동했습니다. 공통 up의 initialize/doctor/start/health receipt와 DB/API/worker 준비 증거가 통과했습니다. 합성 주문 smoke가 SQL → outbox → Kafka → ES 전달과 동일 요청 키 재시도를 확인했습니다.
- 실제 API를 연결한 브라우저에서 31개 주문의 페이지 이동·전체 검색·상태 필터, 상품 주문·상태 변경·Redis 조회·ID 복사를 확인했습니다. Kafka 중단 후 생성한 주문은 SQL에 남고 검색에는 없었으며, 복구 후 같은 ID의 paid/v2가 반영되자 자동 확인이 종료됐습니다. HTTP 모의 응답이나 CSP 우회를 사용하지 않았습니다. 한국어 폰트로 세 화면 크기의 상세·진단 스크린샷과 가로 넘침을 확인했습니다.
- 전용 스택의 SQL 암호를 변경한 재시작은 doctor에서 실패했고, 여섯 컨테이너 ID와 실행 상태는 그대로였습니다. 설정을 복원한 정상 공통 restart는 단계별 준비·health를 통과하고 기존 주문 34건의 모든 필드를 보존했습니다. 재빌드 후 smoke도 전달·동일 키 재시도를 통과했으며, 실제 API가 빈 중복·알 수 없는 쿼리 파라미터를 HTTP 400으로 거부하는지 확인했습니다.

로컬 실행 증거와 스크린샷은 Git에서 제외되는 `mvp-lab/reports/ui-upgrade-20261003/`에 남겼습니다. 검증용 스택은 종료했고 named volumes는 보존했습니다. 기존 사용자 클러스터를 대상으로 쓰거나 재시작하지 않았습니다. 네 HA 실습을 포함한 전체 배치의 이번 실기동, Podman·원격 엔진, 운영 부하·HA·failover는 이번 증거 범위에 포함하지 않습니다.
